# 路线图

按**风险从高到低**排序，不是按功能从简单到复杂排序。
每个阶段必须先通过验证门槛，才允许进入下一阶段。

---

## 阶段 0：交互验证（当前）

**目的**：在写产品代码前，回答一个可能推翻整个设计的问题：

> 每次 Cmd+Tab 都被拦一下，**我能忍多久**？

这是本项目最大的未验证假设。同类产品的差评里，"拦截太烦"比"拦不住"更常见。

### 做什么

- 用最轻的方式（Hammerspoon 或 单独的小 Swift 原型）做出「切走 → 弹浮层 → 等待 15 秒」的最小闭环
- 不做存储、不做统计、不做配额
- 自己真用 **2 个完整工作日**

### 验证门槛（必须全部满足才进入阶段 1）

| 问题 | 通过条件 |
|---|---|
| 会不会想立刻卸载？ | 第 2 天结束时仍愿意开着 |
| 摩擦时长合适吗？ | 记录每次的真实感受，得出一个可用的初值 |
| 全屏还是小窗？ | 有明确的偏好结论，不是"都行" |
| 有没有出现"绕过去"的行为？ | 如果第二天已经开始肌肉记忆式绕过，机制无效，需换方案 |
| 误报率 | 每天误报（正当切换被拦）不超过 3 次 |

### 失败时的退路

若交互被判定不可忍受，**不硬推**。退回"纯度量"路线：只做 US-3（看板）与 US-4（配额缺口），不做拦截。
度量本身就有价值——它把"我今天感觉很忙"变成"我今天只有 2 个超过 12 分钟的块"。

## 阶段 1：连续块引擎 + 看板

**目的**：把"专注"从主观感受变成可看的数字。

### 前置

阶段 0 通过。

### 做什么

- 采集层（前台应用 / 标题 / URL / 空闲 / 锁屏）
- 判定层状态机 + 迟滞（纯逻辑，先写测试）
- 存储层 heartbeat 事件流 + 原子写入
- 菜单栏看板：当前块 / 今日最长块 / 今日切换次数 / 每小时切换
- 配额读取 `focus.json`，显示缺口

### 不做

浮层、会话锁、白名单模式、备注记录。

### 验证门槛

- 连续块状态机有完整单测，覆盖所有迁移与迟滞边界
- 跑满 3 天，人工抽查 20 个 session，判定结果与自身感受一致率 ≥ 80%
- 与 time-audit 的次日数据做交叉验证：同一时段的项目归属不出现方向性矛盾

### 已知风险

- **presence 判定容易失效**：Alma recorder 的记录里 122 个 session 有 119 个被判"离开"，说明纯空闲计时在这台机器上不可靠（大量阅读与思考时间）
- 对策：用三取二 + 迟滞（见 architecture），并在阶段 1 实测误判率

## 阶段 2：摩擦与回位

**目的**：把度量变成干预。

### 前置

阶段 1 通过，且看板数据证明"确实存在大量碎块"。

### 做什么

- 切换浮层（US-2），接入阶段 0 得出的最佳交互参数
- 中断现场封存 + 「我停在哪」恢复显示（US-5）
- 全局热键收杂念（US-5）
- 会话锁（US-1 的强化版）

### 不做

白名单模式、临时放行。

### 验证门槛

- 连续 5 个工作日，每日 ≥12 分钟块数有上升趋势
- 每日误报 ≤3 次
- 不出现"为了躲浮层而干脆不开工具"

### 会话锁的取舍（需 ADR）

自用场景下"扛强杀"是否必要？两种立场：

- **要**：不扛强杀的锁是心理安慰（Flow 的 Commitment Mode 强杀即解除就是反例）
- **不要**：单人自用，真正的约束力来自"我不想骗自己"，而不是技术防线；做扛强杀的锁成本高（launchd + 磁盘状态 + 时间戳校验）且容易过火

在阶段 2 开始前写 ADR 定这个。默认倾向：**先做"重启后可恢复"，不做"不可强杀"**。

## 阶段 3：白名单模式

**目的**：拦住"切到另一个正事"——这是原始需求里最核心的部分。

### 前置

阶段 2 通过，且浮层已被证明可忍受。

### 做什么

- 会话内只允许 1–3 个 app 前台，越界应用被隐藏（不 kill）
- 越界记录 + 3 秒确认
- 临时放行通道（15 分钟额度，记录原因）

### 未决

浏览器要不要进白名单？用户大量工作（电商后台、X 调研、文档）都在浏览器里，但浏览器也是切换的主要入口。**必须先写 ADR。**

### 验证门槛

- 不出现"因为白名单挡住正当工作而被迫关掉工具"
- 临时放行使用频率稳定，不持续上升（持续上升说明白名单划定错误）

---

## 阶段 4（可选）：对外可见的专注状态

**目的**：减少外部打断。

`FlowLight` 研究（449 人 / 12 国）显示，物理指示灯 + 自动可打断性判定能让被打断次数降低 46%。

但这条的 ROI 取决于：用户的切换里有多少比例来自"别人来找"。**先用阶段 1 的数据回答这个问题，再决定做不做。**

可选形态：Slack 状态自动切换、菜单栏图标变色、屏幕角落小指示。

---

## 长期不做

| 项 | 理由 |
|---|---|
| 跨设备同步 | 同类产品差评第一来源 |
| 云备份 / 账号 | 单机自用 |
| 移动端 | 问题只在 macOS 上存在 |
| 应用商店发布 | 个人自用，无需签名公证 |
| 多人协作 / 团队看板 | 与"单人自用"边界冲突 |
| AI 自动拆分任务 | 容易变成新的逃避方式（调工具而不做正事） |
