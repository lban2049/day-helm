# 010. 跨应用同任务切换判定与高频切换降噪机制

- 状态：已采纳
- 日期：2026-11-18

## 背景
此前 `SpectrumBuilder.isSwitch` 只要相邻 `EnrichedSpan` 的 `appName`、`bundleId` 或原始 `windowTitle` 不等即记为一次切换，且 `DayHelmEngine.ingest` 未做瞬时过渡过滤与标题抖动合并。这导致两类高误报：
1. 网页加载、未读数跳动或 `Cmd+Tab` 路过某窗口即被计入切换。
2. 实际工作中的「跨应用闭环协同」（如 `T3 Code / IDE ↔ Terminal ↔ 浏览器文档/本地预览`、`抖店 ↔ Finder ↔ Preview`）在 10 分钟内很容易达到 10 次往返并触发「检测到高频切换」，且首 5 分钟内的切换热度按 300s 分母外推成 `180/h` 等虚高值。

## 候选方案
- **方案 A（仅上调阈值）**：简单把 `thrashingMinSwitches` 调高到 25 或只看 `bundleId` 变化。代价：跨 2~3 个应用的正常高频协同仍会在高频操作时误报，且无法识别真正切去 IM/娱乐应用的分心。
- **方案 B（去噪 + 分层同任务亲和度 + 闭环工作集门控）**：
  1. 在 `EventMerger` 与 `SwitchClassifier` 中对易变标题抖动（未读数、时钟、百分比、省略号）归一合并（同时保留独立编号如 `Tab 0` / `PR #12`），并过滤 `< 4s` 的瞬时过渡窗口。
  2. 分层判定跨应用过渡是否属于同一类任务：共享项目/仓库锚点 → 同 `TaskBudget` 归属（含新增可选 `appBundleIds` / `domains`）+ 纯辅助工具（`Finder` / `Preview` / 启动器等）桥接豁免 → 同工作流角色簇（研发/设计电商/研报写作），同时对 IM/娱乐等打断型上下文强制计数不豁免。
  3. 在滑动窗口增加「闭环工作集门控」：只有独立活跃上下文 `distinctContexts >= 4` 或切入打断型上下文 `>= 4` 时才判定为高频乱切；仅在 `<= 3` 个非打断上下文间往返对照视为闭环协同。
  4. `recentSwitchStats` 仅统计有效跨任务切换，并将最小观测分母从 `300s` 提升至 `600s`。

## 选择
选择 **方案 B**，新增 [`SwitchClassifier`](../../Sources/DayHelmCore/SwitchClassifier.swift) 并集成至 `EventMerger`、`SpectrumBuilder` 与 `DayHelmEngine`。

## 理由
1. **关键常量依据**：
   - `minEffectiveDwellSeconds = 4.0`：略高于 `Cmd+Tab` / 启动器唤起并离开的典型驻留（1–3s），确保只过滤路过窗口而保留真实短暂查看。
   - `thrashingMinDistinctContexts = 4`：跨应用协同绝大多数集中在「主工具 + 辅助/参考/终端」2–3 个上下文闭环；达到 4 个及以上独立上下文且平均停留 `< 45s` 时，才具有明显的扇出打散特征。
   - `thrashingMinInterruptSwitches = 4`：即使仅在 2–3 个应用间往返，只要频繁切入微信/飞书/B站等打断型上下文，依然需要被及时识别提醒。
   - `recentSwitchStats` 最小观测分母 `600.0s`：与 10 分钟检测窗口对齐，消除刚启动前几分钟外推速率翻倍的虚高噪声。
2. 零配置下即可覆盖绝大多数开发、设计电商、研报与通用三窗口对照场景，同时支持通过 `TaskBudget.appBundleIds` / `domains` 进一步精确归属。

## 推翻条件
如果连续使用 5 个工作日后出现以下任一情况，需重开本决策：
1. 真实分心场景（如在 3 个非列表内娱乐站点之间来回切）因未命中打断词库且上下文 `<= 3` 而漏报；或
2. 某类高频跨应用正常协作固定涉及 `>= 4` 个独立上下文且不在同一工作流簇内，导致仍频繁误报，需补充用户可配置的工作流簇白名单或按项目聚合。
